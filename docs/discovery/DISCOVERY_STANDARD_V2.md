# Discovery Standard v2 — value before novelty

**Applies to:** product/workflow value analysis (reference)
**Introduced by:** #198
**Status:** retained reference; execution routing superseded by D-091

Use `DISCOVERY_EXECUTION.md` for current work and `RUN_PROMPT.md` for session
continuation. This value-analysis frame does not impose adoption tests on historical
evidence research. Its former issue numbers do not schedule work.

## Principle

> **EXISTING ≠ USELESS. DIFFERENT ≠ VALUABLE. NOVEL ≠ DEMANDED. COMPETITION ≠ VALIDATION. EVIDENCE DECIDES.**

The project protects its validated research/release core. Discovery exists to find or reject evidence-backed extensions, improvements and adjacencies. It is not a mechanism for rebuilding a speculative feature backlog.

## Calibration: what “proven core” means here

The Atlas has strong **internal project evidence** for:
- claim-specific provenance;
- explicit abstention/unknown/inconclusive states;
- temporal/spatial inference guards;
- separation of law, practice, network participation, research coverage and geometry;
- tiered C0/C1/selective-C2 research/release workflow;
- immutable/reconstructible release discipline;
- a small static evidence register/map candidate.

This does **not** mean external-user demand, adoption, willingness to switch, willingness to pay or public-product value is proven.

Those remain separate hypotheses unless supported by direct evidence.

## Mandatory discovery frame

For any material opportunity, answer only the parts that matter.

### 1. User / circumstance / job

State:
- who the relevant user is;
- in what circumstance the need arises;
- what progress they are trying to make;
- what they do today;
- what happens if they fail;
- what evidence says the job is real.

Possible alternatives include a competitor, adjacent product, spreadsheet, GIS, literature search, notes/Zotero, general-purpose model, expert workflow, manual combination, accepting the cost, or doing nothing.

Never invent an external user need merely because the project can technically serve it.

### 2. Novelty is separate from value

For each capability, record:

**Novelty status**
- novel;
- uncommon;
- novel combination;
- common;
- commodity/expected;
- unknown.

**Strategic relevance of novelty**
- central;
- supporting;
- incidental;
- irrelevant.

A capability may be common and valuable, or novel and unwanted.

### 3. Relative-advantage hypothesis

Use:

> For **[specific user]**, in **[specific circumstance]**, our approach may be chosen over **[current alternative]** because **[specific advantage]**, despite **[adoption/switching cost]**.

Then separate three questions:

1. **Difference** — does the advantage actually exist?
2. **Importance** — does this user care?
3. **Consequence** — is it large enough to change behaviour, adoption, continued use or another meaningful outcome?

Do not collapse them.

### 4. System-level value

A feature is not the only unit of analysis.

Where relevant inspect:
- product;
- product system;
- research workflow;
- integration;
- service;
- channel/distribution;
- segment/positioning;
- trust/governance;
- operating/activity system;
- complementarity with the existing core.

Commercial pricing/business-model analysis is optional and should be used only where a plausible customer/economic model actually exists.

### 5. Adoption / switching

If the user has a current alternative, identify the dominant friction:
- learning;
- workflow disruption;
- migration/history loss;
- integration replacement;
- institutional approval;
- trust/risk;
- inconvenience;
- financial or time cost.

If the alternative is non-consumption, ask whether the improvement is large enough to create use at all.

Treat adoption claims as hypotheses until behavioural evidence exists.

### 6. Evidence labels

Every material conclusion should be one of:

- **OBSERVED** — directly supported by strong project/user/market evidence;
- **SUPPORTED INFERENCE** — reasonably inferred from credible evidence;
- **HYPOTHESIS** — plausible but materially untested;
- **UNKNOWN** — insufficient evidence.

Competitor marketing proves what the competitor claims, not what users experience.

Prefer behaviour over stated preference, relevant-segment evidence over generic market evidence, and independent signals over one anecdote.

### 7. Red team before experiment

Attack the strongest credible case that:
- current alternatives are already good enough;
- pain is weak or infrequent;
- differentiation is cosmetic;
- adoption friction dominates;
- distribution/reach is poor;
- the user/segment is wrong;
- implementation/maintenance cost dominates;
- complexity dilutes the core;
- another category solves the job better;
- apparent whitespace is caused by incomplete research.

No strawmen.

### 8. Experiment contract

Only a surviving uncertainty becomes an experiment.

Record:
- hypothesis;
- why it matters;
- current evidence;
- falsifier;
- target user/sample;
- method;
- behaviour/signal;
- encouraging evidence;
- disconfirming evidence;
- decision that follows.

Use the cheapest experiment that can materially change belief. Do not build a feature to learn whether anyone wants it.

## Decision states

### REJECT NOW
Strong contrary evidence, strategic conflict or no plausible path to meaningful user value.

### PARK
Potentially interesting, but too weak, too remote from the core or lower information value than current uncertainties.

### DISCOVERY CANDIDATE
Credible value hypothesis remains but a critical uncertainty is still unresolved.

### RUN EXPERIMENT
The critical uncertainty is important and can now be tested cheaply enough.

### PROMOTION CANDIDATE
Stronger evidence, preferably behavioural, suggests material value and justifies considering a separately authorized delivery item.

**Desk research cannot by itself produce PROMOTION CANDIDATE.**

## Compatibility with pre-v2 dispositions

For older discovery records:
- **REJECT** ≈ REJECT NOW;
- **PARK** = PARK;
- **REVISE** ≈ DISCOVERY CANDIDATE;
- **ADOPT_FOR_EXPERIMENT** ≈ RUN EXPERIMENT.

Do not rewrite historical records solely for terminology.

## Portfolio discipline

Discovery optimizes **information gain**, not candidate count.

Keep only the smallest experiment set capable of materially changing:
- the product thesis;
- understanding of the relevant user/job;
- relative advantage;
- the value of the current core;
- whether an adjacency deserves continued attention.

The burden of evidence rises with distance from the proven research/release core.

Feature count is not progress.
