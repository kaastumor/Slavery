# Historical Slavery Atlas — MVP v0.1 Delivery Plan

**Parent:** #174  
**Decision basis:** D-080  
**Status:** active delivery horizon  
**Canonical historical release:** v0.6.1 remains unchanged

## Product goal

Crystallize the valuable surviving project core into the smallest useful Historical Slavery Atlas:

> **immutable R1 candidate package + neutral world map + explicit geometry/research states + compact evidence register**

This is a technical MVP candidate, not automatic publication or canonical promotion.

## MVP user story

A user opening the Atlas should be able to:

1. see a neutral world outline even where evidence or historical geometry is missing;
2. distinguish reviewed, inconclusive, unresearched, held and geometry-unresolved states;
3. select a reviewed target and read:
   - strongest bounded proposition;
   - required abstention;
   - evidence locus / inference extent;
   - exact source/version references;
   - review state;
   - language/access limitation;
   - temporal applicability;
   - geometry state;
4. understand that unresearched / inconclusive / unresolved != absence;
5. use the Atlas without a live database/API dependency for the evidence core.

## Architecture baseline

Reuse:
- existing Vite + TypeScript frontend;
- existing MapLibre map;
- R1.6 immutable candidate/QC artifacts;
- current test/sanitation/CI system.

Default MVP serving model:
- static/read-only candidate bundle;
- generated from immutable R1 inputs;
- no production mutation.

Do **not** add unless a later discovery experiment earns it:
- backend/API service;
- database migration;
- authentication;
- frontend framework replacement;
- graph/vector/search infrastructure;
- bespoke ontology engine;
- new universal P-level/intensity field.

## Delivery method

Industry-standard controls, kept lean:

- one product goal / one active delivery horizon;
- one canonical backlog: repository-root BACKLOG.md;
- GitHub issues are atomic work items;
- short-lived branches and PRs;
- WIP = 1 for the autonomous worker;
- explicit dependencies;
- Definition of Ready before work;
- Definition of Done before merge;
- CI + sanitation mandatory;
- risk/decision changes recorded in Project Health / Decisions Log;
- release gate before discovery;
- discovery separated from delivery.

### Work-item flow

`READY -> IN PROGRESS -> PR/REVIEW -> DONE`

Blocked work stays blocked. The worker never skips forward because another task is easier or more interesting.

### Definition of Ready

An issue is READY only when:
- title begins `AUTO READY —`;
- parent/product goal is named;
- dependencies are closed;
- question/scope is bounded;
- acceptance criteria are explicit;
- prohibited scope is explicit where material;
- required data/permissions are available.

### Definition of Done

A delivery issue is DONE only when:
- smallest acceptance slice is implemented;
- adversarial attack has a recorded disposition;
- relevant tests and sanitation pass;
- CI is green;
- no hidden historical inference or source-of-truth fork was created;
- PR is merged;
- issue is closed;
- project state is reconciled only where evidence changed it.

## Kill / shrink rules

Shrink or stop the MVP if:
- static candidate data cannot preserve the R1 contract without rebuilding a backend;
- the existing web app cannot be adapted without reintroducing P-level-first semantics;
- geometry handling requires invented precision;
- evidence register loses abstention/provenance/review state;
- the simplest ordinary map/register remains clearer than an added interaction.

No feature is retained because effort was already spent on it.
