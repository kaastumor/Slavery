# R1.8 Sponsor Usability + Release/No-Release Gate

**Issue:** #203  
**Parent programme:** #159  
**Date:** 2026-09-24  
**Input:** R1.7 TECHNICAL_MVP_CANDIDATE  
**Canonical historical release:** v0.6.1 (unchanged)

## Purpose

This gate finishes R1 as a bounded programme.

It asks whether the current R1 candidate is coherent, honest and usable enough to carry forward as an explicitly non-canonical research artifact.

It does **not** test external demand, product-market fit, willingness to switch or independent historical validity.

Those remain separate questions.

## Red-team correction to the project plan

The initial post-reset plan proposed:

1. sponsor usability review;
2. close R1;
3. freeze project identity;
4. run external expert audit.

That sequence was too tidy.

### Attack 1 — sponsor review could be mistaken for user validation

The sponsor is not a substitute for an external historian/user sample.

**Correction:** R1.8 is a release/no-release gate only. It can judge artifact coherence and honesty, not external value.

### Attack 2 — blocking all #200 preparation on R1.8 wastes time

The #200 experiment protocol is valuable regardless of whether R1 publishes.

**Correction:** freeze the protocol now and allow recruitment feasibility work in parallel.

Participant case execution waits for the R1.8 artifact decision.

### Attack 3 — “PUBLISH” was ambiguous

Publishing a candidate could be confused with replacing the canonical historical release.

**Correction:** use **PUBLISH_CANDIDATE**.

This means an explicitly non-canonical research candidate/preview unless a later canonical-release decision says otherwise.

v0.6.1 remains canonical.

### Attack 4 — closing R1 on REWORK would hide unfinished release work

A technical candidate is not the same as a completed release programme.

**Correction:**
- PUBLISH_CANDIDATE → close R1;
- HOLD_NO_RELEASE → close R1;
- REWORK → keep R1 open and fix only concrete release blockers.

### Attack 5 — freezing project identity before external evidence would bias discovery

Calling the project definitively “method/package” before #200 succeeds would convert a hypothesis into doctrine.

**Correction:** treat “auditable evidence method/package + coverage protocol + optional Atlas surface” as the **current working hypothesis**, not a final identity decision.

## Review boundary

Review the actual candidate, not repository prose.

No feature ideas should be added during this gate.

Defects must be concrete and release-blocking.

## Sponsor review questions

### A. Research-state comprehension

Without opening methodology docs first:

- Can you distinguish:
  - reviewed bounded-supported;
  - reviewed inconclusive;
  - planned/unresearched;
  - held;
  - C0-only?
- Is it obvious that unresearched/inconclusive/held do **not** mean historical absence?

### B. Reviewed-target comprehension

Open at least one reviewed bounded-supported target and one reviewed inconclusive target.

Can you identify:

- strongest bounded proposition;
- required abstention;
- evidence locus;
- inference extent;
- temporal precision;
- exact source/version evidence;
- source-family / dependency information;
- review/access limitations?

### C. Temporal honesty

- Does anchor navigation feel discrete rather than falsely continuous?
- Does the interface make exact / period-level / near-anchor / unknown distinctions understandable?
- Is BCE display understandable and not misleading?

### D. Geometry honesty

All 77 target geometries are currently unresolved.

Review whether:
- this is clearly visible;
- neutral land remains useful geographic context;
- unresolved geometry could be mistaken for historical absence;
- calling the product an “Atlas” currently feels misleading, merely limited, or acceptable.

### E. Candidate/review status

Check whether the surface makes clear that:
- this is a candidate;
- it is non-canonical;
- review is internal/adversarial rather than independent;
- v0.6.1 remains canonical.

### F. External-audit readiness

Would you be comfortable using the frozen evidence packet—not the product UI itself—as material for #200 with external reviewers?

If not, identify the exact blocker.

### G. Practical coherence

Choose one:

- **coherent evidence artifact with a map surface**;
- **technically correct but practically awkward**;
- **methodology exposed through UI without enough coherence**;
- **other**, with a concrete explanation.

## Allowed dispositions

### PUBLISH_CANDIDATE

R1 closes successfully.

The candidate may be published as an explicitly non-canonical research artifact/preview.

No canonical promotion is implied.

### HOLD_NO_RELEASE

R1 closes successfully with no publication.

Artifacts remain preserved and reconstructible.

This is a valid release-programme outcome.

### REWORK

R1 remains open.

Only defects identified by this gate may be fixed.

No new feature, historical-research or geometry-expansion horizon is allowed.

After fixes, rerun R1.8.
