# Semantic Interoperability Evaluation

**Status:** evaluation-only. This document does not change the canonical PostgreSQL/PostGIS model.

## Objective

Define how the atlas can interoperate with semantic-web and cultural-heritage ecosystems without making RDF/Wikibase the canonical research store.

The current working principle is:

```text
canonical relational research model
        |
        v
reviewed release / publish materialization
        |
        +--> JSON/API
        +--> geospatial/vector-tile outputs
        +--> RDF/JSON-LD interoperability export
                |
                +--> SKOS vocabularies
                +--> PROV-O provenance mapping
                +--> selected CIDOC CRM / Linked Art mappings
                +--> SHACL validation
```

## 1. SKOS — controlled vocabulary publication

SKOS is a W3C Recommendation for sharing and linking knowledge-organization systems such as thesauri, classifications and taxonomies.

### Good atlas fit

Potential SKOS concept schemes:

- practice types;
- external participation types;
- evidence roles;
- legal-event categories;
- geometry-accuracy vocabulary;
- other evolving historical/research vocabularies.

Useful properties include preferred/alternative labels, broader/narrower relationships and mapping relations to external concept schemes.

### Boundary

SKOS should describe **concept vocabularies**, not become the evidence/claim ontology. A territorial-practice claim is not merely a SKOS concept assignment.

**Assessment:** strong fit for published controlled vocabularies.

Reference: W3C SKOS Recommendation.

## 2. PROV-O — provenance interchange

PROV-O is a W3C Recommendation for representing and interchanging provenance across systems.

### Good atlas fit

Potential mappings:

- SOURCE_ASSET / RAW_RECORD → `prov:Entity`;
- INGEST_RUN / OCR / HTR / extraction / normalization → `prov:Activity`;
- researcher, tool/model, institution → `prov:Agent`;
- normalized candidate generated from raw record → `prov:wasDerivedFrom`;
- derivative generated by an OCR/HTR activity → `prov:wasGeneratedBy`;
- research/review activity associated with researcher/tool → `prov:wasAssociatedWith`.

This is especially useful for publishing machine-readable lineage across different toolchains.

### Boundary

PROV-O does not replace CLAIM_SOURCE. Historical evidentiary support is a domain-specific relationship; computational provenance is related but not identical.

**Assessment:** strong fit for release/export provenance.

Reference: W3C PROV-O Recommendation.

---

## 3. CIDOC CRM / Linked Art — cultural-heritage interoperability

Linked Art is a practical cultural-heritage data model built on CIDOC CRM. It uses an event-oriented model and covers people/organizations, places, concepts, events, archival/textual resources and specific assertions.

### Good atlas fit

Potential external mappings:

- ACTOR → Person/Group;
- SPATIAL_ENTITY → Place;
- SOURCE/SOURCE_VERSION → Linguistic/Digital/Information objects as appropriate;
- LEGAL_EVENT and selected historical events → event/activity patterns;
- identifiers and names → Linked Art identifier/name patterns;
- specific assertions/provenance → selected Linked Art assertion patterns.

This could make atlas releases easier to link with museum/archive/library ecosystems.

### Boundary

CIDOC CRM is intentionally broad and semantically rich. The atlas should not distort its internal claim-centric research model merely to mirror CRM classes. Mapping belongs in an interoperability profile/export layer.

**Assessment:** useful mapping target; not a canonical schema replacement.

Reference: Linked Art data model / CIDOC CRM foundation.

## 4. SHACL — semantic export validation

SHACL is a W3C language for validating RDF graphs against explicit shapes/constraints.

### Proposed atlas use

Once an RDF/JSON-LD release export exists, SHACL can validate rules such as:

- every exported claim has a stable identifier;
- every evidence relationship points to an exact source/version;
- required labels/identifiers are present;
- publication/release metadata are present;
- SKOS concepts use expected schemes;
- provenance nodes have required links.

### Version policy

The stable SHACL Recommendation remains an appropriate baseline. A newer SHACL 1.2 Core is currently a W3C Working Draft (August 2026); do not make a draft specification a release dependency without a deliberate decision.

### Boundary

SHACL validates an RDF representation. It is not a substitute for PostgreSQL constraints, migration tests, claim review or historical QC.

**Assessment:** strong fit after the first semantic export exists.

## 5. Wikibase — explicitly not the canonical store

The Enslaved project is a valuable peer case. Later work by its ontology team reports that adapting an OWL ontology to Wikibase was less straightforward than expected because Wikibase and OWL-style modeling differed in data validation and provenance representation. Their production graph remained conceptually close to the ontology but not identical.

This is directly relevant to the atlas:

- Wikibase has useful collaborative statement/qualifier/reference features;
- but introducing it would create another data model and synchronization boundary;
- our current PostgreSQL claim/source model already enforces distinctions that are central to the atlas;
- semantic interoperability can be achieved through exports without replacing the canonical store.

**Assessment:** do not introduce Wikibase now. Reconsider only if a future multi-editor research workflow demonstrates a concrete unmet need.

Relevant peer work:
- Shimizu et al., *The Enslaved Ontology* (2020).
- Zhou et al., *The Enslaved Dataset* (2020).
- Shimizu et al., *Ontology Design Facilitating Wikibase Integration* (2022).
- Shimizu et al., *The Wikibase Approach to the Enslaved.Org Hub Knowledge Graph* (2023).

## Proposed semantic-publication stack

```text
PostgreSQL/PostGIS
  canonical claim-centric model
           |
           v
release-specific export transformer
           |
           +--> SKOS concept schemes
           +--> domain RDF/JSON-LD claim graph
           +--> PROV-O computational/research lineage
           +--> Linked Art/CIDOC-aligned entities where useful
           |
           v
SHACL validation
           |
           v
versioned semantic release artifact
```

## Acceptance criteria before implementation

Do not build the semantic export until:

1. release membership/reconstruction is explicit;
2. SOURCE/SOURCE_VERSION migration is stable;
3. the global evidence sheets have been semantically migrated;
4. the competency questions establish which graph relationships are actually useful;
5. URI/identifier policy is defined;
6. a first mapping document shows which atlas semantics map cleanly and which remain atlas-specific.
